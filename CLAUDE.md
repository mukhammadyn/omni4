# omni4

ERP на платформе ucode: модули CRM, HRMS, Склад, Финансы, Проекты
поверх того же бэкенда (object builder, auth, company, function service).

Кодовая база — форк new-ucode (переписанной с нуля админки ucode),
скопирован 2026-09-30 с коммита `1dfc535` от 2026-09-24. Всё, что
админка умела к этому дню, omni4 умеет тоже; ERP-модули строятся
поверх. Где мы сейчас — [docs/STATUS.md](docs/STATUS.md).

Писать в них нельзя: ни правок, ни новых файлов, ни `sed -i`, ни `git`
с изменением состояния (`commit`, `checkout`, `stash`, `restore`).
Правка там — отдельная задача в отдельном репозитории с отдельным
ревью; из этого репозитория она уезжает незамеченной.

`Edit` и `Write` по этим путям запрещены в `.claude/settings.json`.
Дыру в Bash (`sed -i`, `git commit`, `> файл`) закрывает хук
`.claude/hooks/no-write-to-readonly-repos.py`: он отклоняет команду,
в которой есть И путь в такой репозиторий, И меняющий глагол. Чтение
(`grep`, `sed -n`, `cat`, `git log`, `git diff`) проходит.
Хук — последний рубеж, а не замена пониманию, зачем они лежат рядом.

`ucode_go_admin_api_gateway`, `ucode_go_object_builder_service`,
`ucode_go_auth_service`, `ucode_go_company_service`,
`ucode_go_function_service` (функции и микрофронтенды).

Первый источник при вопросе «а как оно на самом деле»: что делает
ручка, что пишет в базу, какие поля обязательны.

что не так. Если фронт вынужден её обходить, обход помечается
комментарием со ссылкой на место в Go-коде, а сама ошибка —
в [docs/backend-notes.md](docs/backend-notes.md).

### Старая админка

**Это спецификация поведения, а не исходник.** Оттуда переносится
ответ на вопрос «что»: что делает фича, какие эндпоинты дёргает, какие
поля в ответе, какие крайние случаи покрыты.

Никогда не переносится «как»: код, структура файлов, имена. В том
репозитории 290k строк, четыре поколения формы, три реализации
таблицы, 359 ветвлений по legacy-флагам и живые баги. Он не эталон.

### Прототип omni4

Статичные HTML-страницы, по одной на экран; стили и скрипт встроены
в каждую. Меню модулей — `NAV`, `NAV_HRMS`, `NAV_PM` и `MODULES`
в `<script>` любой страницы.

Из прототипа берётся «что» и «как выглядит»: какие экраны есть
в модуле, что на них, токены и плотность. Код не берётся — это
данные-заглушки и один файл на страницу.

Референс — файлы в корне `crm/`. `notion/` — их копия,
`_backup-blue/` — прошлый вариант, не референс.

## Правила

- **Границы.** `shared/` не зависит ни от чего. `features/*` импортирует только `shared/` и `index.ts` соседней фичи. `routes/` импортирует фичи, обратно — нет. Проверяется `pnpm lint`.
- **Запросы** объявляются только в `features/<имя>/api/`. Компонент вызывает готовый хук.
- **Ключи кэша** — только из `shared/lib/query-keys.ts`. Строковых литералов нет.
- **Цвета** — только токены из `app/styles.css`. Захардкоженный цвет ломает тёмную тему.
- **Одно имя — один источник.** Бэкенд отдаёт одно и то же под разными именами. Нормализация — один раз, в `features/*/api/`. `a || b || c.d` в компоненте запрещён; истина ищется в схеме БД и proto.
- **Никаких legacy-веток.** `new_design`, `new_router`, `new_layout` не читаются: всегда новое поведение.

## Зависимости

**Перед установкой или добавлением любой зависимости — проверить актуальную
версию в реестре, а не писать по памяти:**

```
npm view <пакет> version          последняя стабильная
npm view <пакет> dist-tags        есть ли rc/beta/next
```

(`npm view` — это запрос к реестру, он работает и в проекте на pnpm.)

Модель помнит версии на момент обучения, и они устаревают. При первой
сборке new-ucode разрыв был на мажор почти везде: vite 6→8,
typescript 5→7, eslint 9→10, vitest 2→4, zod 3→4, react-table 8→9.

**Исключение — совместимость.** Берётся последняя стабильная, **которую
поддерживает остальной инструментарий**. Если самая свежая версия ломает
соседа, ставится последняя работающая, а причина пишется рядом.

Живой пример, который сейчас в `package.json`:

```
typescript        5.9.3   не 7.0.2
```

typescript-eslint 8.67.0 (последний стабильный) явно отказывается работать
с TS 7, а без него ESLint не парсит `.ts` вообще. Версию можно поднять,
когда выйдет стабильный typescript-eslint с поддержкой TS 7.

Бета, rc, alpha, canary — не ставим.

## Команды

Пакетный менеджер — **pnpm**, версия закреплена в `package.json`
(`packageManager`). npm и yarn не использовать: их лок-файлы разойдутся
с pnpm-lock.yaml, а плоский node_modules скроет незадекларированные
зависимости.

```
pnpm install
pnpm dev            сервер на 7777
pnpm build          tsc + vite build
pnpm lint           границы и типы
pnpm test           vitest
pnpm gen:api        типы из swagger бэкенда
pnpm gen:routes     routeTree.gen.ts
```

Pre-commit (`.githooks/pre-commit`) гоняет lint и typecheck. Включается
один раз на клон: `git config core.hooksPath .githooks`.

**pnpm не поднимает транзитивные зависимости.** Если пакет импортируется
из кода — он объявляется в `package.json` явно, а не берётся из-под
чужой зависимости. Ошибка `ERR_MODULE_NOT_FOUND` на пакете, который
«вроде установлен», означает именно это: `pnpm add -D <пакет>`.
