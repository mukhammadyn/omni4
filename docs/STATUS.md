## Решено 2026-09-30

1. **Module — папка в корне меню с `is_tab`** в одном проекте

2. **Экраны — наши view, дизайн — прототип**
   ([ADR-0011](adr/0011-prototype-design-system.md)). Перерисовывается
   всё, не только view. Недостающие типы view добавляются.
3. **Конструктор остаётся.** Для кого — решается позже.
4. **Имя продукта — omni4.** Переименованы: `<title>`, заголовок
   вкладки вне проекта (`routes/_authed.tsx`), `name` в `package.json`,
   `app.name` и заголовок входа в трёх локалях, ключи `ucode.*` →
   `omni4.*` в localStorage (сессия, язык, UI).
   Не переименовано намеренно — это договор с платформой, а не имя
   продукта: адреса API в `.env*`, папка `ucode` в CDN, тип беседы
   `ucode` у копилота, контракт микрофронтендов (`#ucode-remote`,
   событие `ucode:microfrontend:activate`, `packages/ucode-remote-sdk`,
   имя хоста `ucode-admin` в module federation).
5. **Логотип** — `public/omni4-logo.svg`, `currentColor`; снят с
   `omni4_core/omni4-logo.png` (вне репозитория). Знак «o⁴» из тех же
   контуров — в `BrandMark` (сайдбар, вход) и `public/favicon.svg`.
   **Только omni4:** у new-ucode остаётся знак ucode, логотип туда
   не переносится.

## HRMS: Вакансии (2026-10-08)

Таблица — наш TABLE, как `tableView` прототипа. Колонки view
(в проекте): Название · Статус · Приоритет · Отдел · Рекрутер ·
Нанимающий менеджер · Филиал · Формат. За ними вычисляемые колонки
`features/hrms` (`useVacancyColumns`, проп `extra` у `DataGrid`):
Зарплата · Воронка · Кандидаты · Нанято · Открыта · Дедлайн. Они только
читаются; у других таблиц их нет. Счётчики считает фронт по
`hr_candidates`: FORMULA их не досчитывает (backend-notes, «Поле FORMULA»).
У шести LOOKUP `hr_vacancies` записан `attributes.label` — шапка
показывала «Сотрудники» вместо «Рекрутер».

**«Карточки»** — фиксированный тип view `VACANCIES` (`FIXED_VIEW_TYPES`,
как ORG; заведён через API на пункт «Вакансии»), компонент
`VacancyCards` — `.rc-card` прототипа: статус и приоритет, дедлайн,
отдел · филиал · сколько открыта, зарплата, воронка с тремя последними
этапами, кандидаты, нанято, команда найма. Группировки карточек нет.

**«Планирование»** — фиксированный тип `VACANCY_PLAN`, компонент
`VacancyPlan` — `planView` прототипа: группы (филиал, отдел, статус,
приоритет, рекрутер) → вакансии, шесть месяцев «нанято / план», итоги
«План · Работают · Нанято · Уходят · Нужно нанять», «Итого». Грузит все
вакансии без страниц, как ORG; закрытые тоже, как в прототипе.
Источники свои, а не прототипа (там «Работают» включают нанятых,
а «Уходят» выдуманы): «Работают» — только сотрудники той же должности,
отдела и филиала, не уволенные и не нанятые из этой вакансии;
«Нанято» — кандидаты вакансии со статусом «Нанят», отдельно, потому что
карточку сотрудника нанятому заводят не всегда (сейчас ни у одного
сотрудника нет `hr_candidates_id`); «Уходят» — работающие с датой
увольнения впереди (`model/vacancy-plan`). Группировка
и период помнятся у человека по view (`ui-store`, `viewState`,
`ui/plan-settings`), там же «Строка» — что видно под названием —
и высота строки. Группировка и «Строка» — кнопки в строке вкладок
(`VacancyPlanTools`), период — подшапка экрана;
«Сегодня» опору стирает. Вкладки: Планирование · Таблица · Карточки
(`PUT /v2/views/{slug}/update-order`).

**Страница вакансии** — `/vacancies/$itemId` (`VacancyPage`), как
`vacancy.html` прототипа; вакансия из любого вида открывается ей, а не
drawer'ом, как сотрудник. Шапка: приоритет, отдел, филиал, формат,
сколько открыта, зарплата, «x из y нанято», дедлайн, команда; статус —
выбором. Вкладки: «Воронка» — канбан по этапам воронки вакансии,
перетаскивание меняет этап кандидата (`stage_changed_at` — сейчас)
и пишет переход в `hr_candidate_stage_history` (с этапа → на этап,
статус, когда, кто — своя строка `employees` из токена; у ADMIN её
нет, поле пустое). Пишет фронт: событий на `hr_candidates` у проекта
нет, бэкенд историю не ведёт (`model/stage-history`),
ниже «Завершённые» с возвратом в воронку; «Кандидаты» — таблица
с поиском; «Информация» — тексты (HTML — редактором в режиме чтения)
и карточки полей. Карточки и строки полей — общие со страницей
сотрудника (`ui/page-parts`). Оценка «x/10» — средняя по
`hr_candidate_evaluations`: поле `hr_candidates.score` — FORMULA без
настроек и не считается.

**Формы** — `edit()` и `form()` прототипа, части общие
(`ui/record-form`: секция, поле по типу из схемы, плашки, переключатель,
полоса внизу; проверка — `rowErrors`, как у ячейки):
- «Редактировать» — `?tab=edit` (`VacancyForm`): восемь секций
  с оглавлением, подсвечивается секция на экране; правки копятся
  в черновике и уходят одним PUT по «Сохранить».
- «Создать» вакансию — `/vacancies/new` (`NewVacancy`), та же форма
  с умолчаниями прототипа; «Создать» из любого вида `hr_vacancies`
  ведёт сюда, а не в drawer. Воронка — `is_default`.
- Новый кандидат — `/candidates/new?vac=` (`NewCandidate`): из «+ Кандидат»
  вакансии и из «Создать» меню `hr_candidates`. Резюме прикрепляется
  к `resume` без разбора; первый комментарий — в `notes`; встаёт
  на выбранный этап, «в работе», с записью в истории.
- `channels` и `languages` получили варианты в схеме (2026-10-08),

## HRMS: Кандидаты (2026-10-14)

Один TABLE view на `hr_candidates`, вкладки прототипа (Активные ·
Нанятые · Отказ · Резерв) — раскладка view по `status` (`group_fields`),
а не view на вкладку. Колонки — как `candidates.html`, «Причина» общая
для всех вкладок в конце. Группировка по умолчанию снята (её поля бэкенд
ставит первыми колонками, backend-notes). На вкладках раскладки —
счётчики, для любой таблицы (`useItemCounts`: запрос `limit: 1` на
вкладку, тем же отбором, что и список, с поиском и фильтрами).

Вкладки раскладки стоят в строке view вместо его имени, когда view
у пункта один (как в прототипе); view несколько — строкой ниже, как было.

Полоса значений — новая настройка view «Полоса значений»
(`attributes.chips_by_id`, наш ключ; у таблицы, списка, галереи):
чипы по значениям поля с цветом и счётчиком, нажатие — отбор человека
по полю. Считается одним запросом из строк (до 500, `ValueChips`),
одноимённые значения склеиваются — этапы у каждой воронки свои.
У кандидатов включена по «Этапу».

**Таблица кандидатов** — фиксированный тип `CANDIDATES` (как VACANCIES;
view кандидатов переведён на него через API), компонент
`CandidatesTable` — `draw()` прототипа: своя таблица, а не DataGrid —
строка в две строки, а высоту строки грида держит виртуализатор.
Кандидат с инициалами, уровнем и метками · вакансия с отделом · этап
плашкой с точкой · оценка по `hr_candidate_evaluations` · источник ·
ожидания · дни на этапе (больше 5 — красным) · отклик. Колонки по
вкладке: активные — Этап · На этапе; нанятые — Выход на работу · Нанят;
отказ и резерв — Причина · Последний этап. В строке: у активных —
следующий этап своей воронки по `sort_order`, у отказа и резерва —
вернуть в работу; оба пишут `hr_candidate_stage_history`
(`useCandidateMoves`, тот же, что у страницы вакансии).

Открыто: полоса этапов видна на всех вкладках, а не только на
активных; иконки вкладок; сортировка по дате отклика по умолчанию
(view её не хранит); скрытие колонок и «Строка» прототипа (город,
уровень, метки); группировка (у типа её нет).

**Страница кандидата** — `/candidates/$itemId` (`CandidatePage`), как
`candidate.html` прототипа; открывается из любого вида `hr_candidates`,
из воронки и «Кандидатов» вакансии. Слева профиль (фото, вакансия,
средний балл, свойства — правятся по «Изменить» тем же ActiveCell)
и документы (`resume` + `attachments`, загрузка в `attachments`).
Справа воронка вакансии кружками: пройдены этапы до текущего по
`sort_order` (у нанятого все) — как в прототипе, без истории: у старых
кандидатов её нет (`model/candidate-steps`). Действия: этап выбором,
«Следующий», «Нанять» (`hired_at` — сегодня), «Отказ» с причиной из
`hr_rejection_reasons` (активные), «Резерв», «Вернуть в работу»
(причина стирается) — всё пишет `hr_candidate_stage_history`, выход
из воронки — с пустым «на этап». «Оценка по этапам» — по
`hr_candidate_evaluations`: балл этапа — среднее; щелчок по баллу
правит свою оценку (своя строка `employees`; у ADMIN — строки без
оценщика), комментарий — новая строка без балла, HTML. «История» —
переходы и отклик. «Ещё»: письмо, Telegram, печать.

«Нанять» ставит и выход на работу — через 14 дней, как в прототипе.
Новый кандидат после «Добавить» открывается своей страницей. У пяти
LOOKUP `hr_candidates` записан `attributes.label` (2026-10-14): вместо
«Источники кандидатов» и «Сотрудники» — «Источник» и «Рекрутер».
Проверено вживую на кандидате: балл (новый и правка), комментарий,
отказ с причиной, возврат, резерв, следующий этап, найм, правка email,
загрузка, просмотр и удаление файла, история.

Догнали прототип (2026-10-14): метки правятся в «Изменить» (ввод
`Tags` из формы кандидата); «Резерв», как и «Отказ», — с причиной
из справочника, причина пишется и в `comment` записи истории;
«Перенести на другую вакансию» («Ещё») — открытые вакансии, кандидат
встаёт на первый этап её воронки, статус не меняется, в истории —
откуда перенесён; у нанятого — «Создать сотрудника» (`employees`:
имя и контакты кандидата, почта — личная; должность, отдел, локация,
формат и тип занятости — вакансии; приём — день выхода;
`hr_candidates_id` — связь) или «Открыть сотрудника», если уже заведён;
печать — только страница, без сайдбара и кнопок (`data-print-page`,
app/styles.css); у файлов — размер и дата из заголовков CDN на HEAD
(`useFileMeta`), имя — без приставки хранилища. Всё, кроме печати,
проверено вживую.

Открыто: средний балл в профиле считается по всем оценкам кандидата,
и после переноса в него входят этапы прежней вакансии.

## HRMS: Посещаемость (2026-10-09)

Пункт «Табель» (`hr_attendance_days`, папка «Время») переименован
в «Посещаемость». Вкладки: Календарь · Список · Табель · Отсутствия ·
Таблица, как в прототипе. «Отсутствия» — view на `hr_requests` в меню
«Посещаемости»: у view своя таблица, и роут берёт схему, права и карточку
по `view.tableSlug`, а не по таблице пункта. Тот же view стоит и на пункте
«Заявки».

**«Список»** — тип `ATTENDANCE`, раскладка `list` (ADR-0016), компонент
`AttendanceList`, как список отметок HRMS (`Time/Attendance`): строка —
день сотрудника (`listOf` в `model/timesheet`); приход, уход,
опоздание, переработка, статус, статус заявки (`review`), источник,
фото прихода и ухода, расстояние, комментарий; «Подтвердить /
Отклонить» в строке, когда отметка ждёт решения. По умолчанию один
день, как в HRMS; неделя и месяц, счётчики статусов с отбором
и порядок «свежие дни, внутри — проблемы» — из прототипа. Страницы
по 20; источник, фото и расстояние — из `hr_attendance_events` только
для сотрудников и дат текущей страницы (`useDayMarks`).

**«Календарь»** — фиксированный тип `ATTENDANCE`, раскладка по умолчанию, компонент
`AttendanceCalendar`. Месяц — как календарь HRMS (`modules/Calendar`):
статус дня значком на цветной плашке (✓, часы, ×, «на работе»,
праздник), отсутствие — одной полосой через свои дни, ждущее решения —
пунктиром и серым (`runsOf` в `model/timesheet`). Неделя и день —
`evView` прототипа: приход, уход, полоса отработанного от смены. Над
сеткой счётчики «Вовремя · Опоздание · Прогул · Отсутствие» за период;
щелчок гасит остальные дни (`statusOf`). Клик по дню — то же окно дня.
Данные, период, поиск — общие с табелем (`ui/attendance-parts`).

**«Табель»** — тип `ATTENDANCE`, раскладка `sheet` (ADR-0016; `FIXED_VIEW_TYPES`,
заведён через API первой вкладкой), компонент `Timesheet`. Логика и UX —
табеля HRMS (`udevs_hrms_admin`, `modules/Time/Sheet`), вид — `sheetView`
прототипа. Сотрудники × дни месяца или недели; в ячейке часы, ×
(прогул), В, П (праздник), код типа отсутствия (О, Б, ДО…) его цветом,
значок «на работе»; жёлтая точка — отметка (`review = pending`) или
заявка ждут решения. Справа итоги: Норма · Часы · Опозд. · Перераб. ·
Дни · Прогулы. Считает `model/timesheet` (тест рядом): день берётся
готовым из строки `hr_attendance_days`, норма — по `hr_shifts`
(`planned_minutes` у дней пустой), отсутствия — `hr_requests` типа
absence с типом из `hr_absence_types`, праздники — `hr_holidays`.
Данные грузит сам (`api/timesheet`), строки view ему не нужны; поиск,
масштаб и период — свои, период помнится по view (ui-store).

Клик по ячейке — окно дня (`TimesheetDay`): приход, уход, отработано,
опоздание, таймлайн и фото из `hr_attendance_events`, «Подтвердить /
Отклонить» для отметки на согласовании, стрелки по дням.

Время отметок записано ташкентскими часами с `Z` — обход в окне дня,
см. backend-notes, «Посещаемость: местное время записано как UTC».

**«Отсутствия»** — пункт «Заявки» (`hr_requests`), фиксированный тип
`ABSENCES`, компонент `Absences`, как AbsenceRequestsView HRMS:
сотрудник, тип (значок и цвет из `hr_absence_types`, причина под ним),
период, дней, статус и цепочка согласования «маршрут x/y»; у ждущих —
«Подтвердить / Отклонить». По умолчанию месяц, как в HRMS; неделя, день,
счётчики «Ожидает · Подтверждена · Отклонена» с отбором и ждущие первыми —
из прототипа. Клик по строке — обычная карточка записи.

Согласование (`model/approval`, как `approvalRuntime` HRMS): маршрут —
активный `hr_approval_routes` того же вида и отдела заявки, маршрут на её
тип отсутствия важнее общего. Пройденный шаг — строка
`hr_request_approvals` (решение, когда, кто — своя строка `employees`
из токена); итог — `status` и `decided_at` заявки: «одобрена», когда
пройдены все шаги или маршрута нет, «отклонена» — сразу. Так лежат

подбирается — отделы процесса при переносе потерялись
(SYSTEM-TABLES-AUDIT). Кто вправе решать шаг (`approver_rule`), экран
не проверяет. Баланс отсутствий (`hr_absence_balance`) при одобрении
никто не пишет: строки там только из импорта 2026-05-15.

**Переход на сотрудника** — как `employee.html#att` / `#abs` прототипа:
имя в календаре и табеле, строка списка — страница сотрудника на вкладке
«Посещаемость»; строка «Отсутствий» — на вкладке «Отсутствия» (карточка
заявки — «глазом»). Адрес — `/employees/:id?tab=attendance|absences`,

после «Работы».

## HRMS: График работы (2026-10-14)

Пункт «Смены» (`hr_shifts`, папка «Время») переименован в «График
работы». Вкладки: Календарь · Шаблоны · Таблица, как `schedule.html`
прототипа. «Шаблоны графиков» перенесены в «Настройки модулей / HRMS»:
у графика своя вкладка шаблонов. Термины — Shift, Shift series, Work
schedule template в CONTEXT.

**Модель.** Прототип хранит смену серией (сотрудники, период, дни
недели, исключённые дни); у нас строка `hr_shifts` — сотрудник × дата,
серию связывает `series_id`. `model/schedule` (тест рядом) разворачивает
серию и шаблон в дни и собирает серию обратно в форму. Правка
и удаление серии — по осям «какие дни × кому» (CONTEXT, Shift series),
строки обновляются на месте; прошлое — норма табеля, не трогается.
Пишется порциями по 1000 через upsert-many с guid от фронта, сначала
запись, потом удаление (`api/schedule`).

**«Календарь»** — фиксированный тип `SCHEDULE`, компонент
`ScheduleCalendar`: сотрудники × дни месяца, недели или дня; смена —
плашка со временем и филиалом, цвет — тип, искра — смена не из шаблона;
пустой день — «Выходной» или «Праздник». Ось «Должность» склеивает
одинаковые смены должности в «N из M». Над сеткой счётчики по типам
с отбором, выходные, люди и часы. Группировка и фильтры по отделу,
филиалу, шаблону — личные, по view (`schedule-settings`). Шаблон
сотрудника — по его сменам в периоде, иначе из карточки.

**Окно смены** (`ShiftDialog`, `shiftModal`): сотрудники, должность,
время с–по или часов в день, тип, один день или период по дням недели
(праздники пропускаются), филиал, проект, комментарий. Из пустой
клетки — новая, из плашки — правка серии; «Сохранить» и «Удалить»
у серии спрашивают, какие дни и кому, и показывают число смен;
«Только <день>».

**«Шаблоны»** — фиксированный тип `WORK_SCHEDULES` на
`hr_work_schedules`, компонент `WorkSchedules`: карточка на шаблон —
неделя или цикл клетками, часы в неделю, перерыв, кто на нём;
дублировать, удалить. Шаблон со сменами впереди не удаляется — сначала
применить другой. Окно шаблона (`TemplateDialog`) пишет строку и семь
дней заново. «Применить» (`ApplyTemplateDialog`): шаблон, сотрудники,
период, филиал, «заменить существующие», «сдвигать цикл»; смены — одной
серией, шаблон — в карточку каждого. «Создать» в шапке — новая смена
или новый шаблон (`ScheduleCreate`).

**Вкладка сотрудника** «График работы» (`EmployeeSchedule`, `schTab`):
неделя сеткой по часам 07–22 или месяц клетками, «Смен: N · X ч».
Щелчок по часу — смена с этого часа, по дню — на день, по смене — её
правка. Встаёт на место вкладки связи `hr_shifts`, как «Посещаемость».
Имя в календаре графика ведёт сюда (`?tab=schedule`).

Живой проект: обоим шаблонам перерыв 300 → 60 минут; 1202 сменам
проставлен шаблон из карточки сотрудника (`hr_work_schedules_id` был
пуст у всех). Сотрудники пишутся PUT по одному — см. backend-notes,
«PATCH строк под токеном пользователя».

Ещё нет: отпуска и значок серии во вкладке сотрудника, раздвигание
перекрытых смен. Не проверено глазами
в браузере.

**Виды смен — справочник (2026-10-16).** `hr_shift_kinds` в настройках
HRMS вместо зашитых `day`/`night`/`remote`: название, цвет, иконка,
время по умолчанию (подставляется в новую смену), «Удалённо» (вместо
филиала — имя вида). Смены, дни шаблонов и цикл шаблона ссылаются на
него через `hr_shift_kinds_id` (ERP-TEMPLATE §1.6). В omni4 таблица
заведена, 1564 смены, 14 дней и 2 шаблона перенесены SQL-ом.
Старые PICK_LIST `hr_shifts.shift_kind`,
`hr_work_schedule_days.shift_kind`, `hr_work_schedules.cycle_shift_kind`
удалены после деплоя PR #12 (2026-10-16). В omni5 справочника нет.

Смены «часов в день» (гибкие) — без `start_time`/`end_time`, норма
в `planned_minutes` (`model/schedule`, `isFlexible`). Плашка «N из M»
открывает серии всех своих смен разом (`OpenShift.seriesIds`).

«Сохранено» в полосе крошек. Без права на правку — только чтение.

**Меню «…»** (строка дерева и полоса страницы): подстраница,
дублировать (без вложенных), переместить в… (своя ветка недоступна),
скопировать ссылку, удалить вместе с вложенными (бэкенд каскада не
делает). **Перетаскивание** в дереве — HTML5: верх строки — перед,
низ — после, середина — внутрь; соседям пишется `sort_order` по
порядку (`dropPlan`, тест рядом). Автор правки — только у правки текста,
заголовка, эмодзи.

**Запросы.** Страницы — без связей: в `hr_kb_articles_id_data` бэкенд
кладёт родителя целиком, с текстом (backend-notes), — 2,6 МБ против 1,1.
Авторы — отдельным запросом к `core_users`. Создание, удаление и правка
меняют кэш на месте, без перезапроса базы: иначе мегабайт на каждую
паузу в наборе, а новая страница появлялась через секунду и по кнопке
жали ещё раз (так в omni4 появились 9 пустых страниц, удалены).

tiptap поднят до 3.32.0 (все пакеты разом).

Живой проект (omni5 и omni4): заведён view `KNOWLEDGE` «База знаний»
первой вкладкой, TABLE — второй. В браузере на omni4 проверены дерево,
страницы с таблицами и списками, меню «/», выноска, чек-лист, таблица,
создание и удаление — запись при этом была отключена локально.
Создание и удаление на omni4 проверены пользователем.

Ещё нет: панель форматирования при выделении (ссылка руками), правка
последних 0,6 с при закрытии вкладки может потеряться, перетаскивание
в браузере мной не проверено.

## HRMS: Тренинги (2026-10-15)

Пункт «Тренинги» (`hr_trainings`, папка «Обучение») — как
`trainings.html` и `training.html` прототипа. Вкладки: Список ·
Календарь. Термины — Training, Participant, Homework в CONTEXT.

**Данные.** Тренинг — `hr_trainings` (тренер — `core_users_id`),
участники — `hr_training_participants`, строка на тренинг × сотрудник
с результатом ДЗ, материалы — `hr_training_materials` (файл или
ссылка). Свои типы view не понадобились.

**«Список»** — TABLE, колонки по прототипу: название, категория,
начало, окончание, тренер, место, статус. За ними вычисляемые колонки
`useTrainingColumns`: «Участники» (аватары и число) и «Домашнее
задание» (полоса «x/y принято»; зелёным принято, жёлтым сдано и ждёт
или на доработке, как в прототипе). Тренинг открывается страницей,
«Создать» ведёт в форму.

**«Календарь»** — обычный CALENDAR по `starts_at` → `ends_at`,
в событии одно название. Цвета по статусу, повестки недели и счётчиков
над сеткой, как в прототипе, у нашего календаря нет.

**Страница** `/trainings/$itemId` (`TrainingPage`): шапка со статусом
выбором, период, тренер, место, категория, ДЗ и срок; описание (HTML,
редактором для чтения); KPI «Назначено · Сдали ДЗ · Принято ·
Отклонено» — они же отбор участников; участники: отдел, статус ДЗ,
комментарий проверяющего, файл, дата, оценка. У сданного ДЗ — «Принять»
(оценка 1–10, отзыв) и «Отклонить» (что доработать); пишется кто
проверил (своя строка `core_users`; у ADMIN её нет — поле пустое)
и когда. Материалы — ссылка открывается, файл скачивается.

**Форма** — `?edit=true` и `/trainings/new` (`TrainingForm`):
«Основное» (плюс поля схемы сверх прототипа: тип, часы, провайдер),
«Домашнее задание», «Сотрудники» (`EmployeePicker`), «Материалы»
(файл на CDN или ссылка). Всё уходит по «Сохранить» (`useSaveTraining`):
тренинг — POST/PUT, у правки только тронутые поля; участники
и материалы — upsert-many, удаление после записи. Новый участник —
«Назначен»; ДЗ включили — у участников «Не сдано», сданное
и проверенное не стирается; сняли — «ДЗ нет» (`model/training`, тест
рядом).

Живой проект (omni5 и omni4): TABLE переименован в «Список», колонки
выставлены; заведён CALENDAR «Календарь». В omni5 в браузере проверены
список, календарь, страница, создание, правка и «Принять» на тестовом
тренинге (удалён). omni4 к этому дню уже на v2 — данные той же формы
(сверено по API), в браузере не открывался.

Ещё нет: «Напомнить» (Telegram), «Дублировать» и «Из шаблона прошлого
тренинга», перетаскивание файлов, порядок материалов, сортировка
по числу участников. «Отклонить» не нажимался в браузере.

## HRMS: Опросы (2026-10-19)

Пункт «Опросы» (`hr_surveys`, папка «Обучение») — как `surveys.html`
(`#list`, `#tpl`) и `survey.html` прототипа; логика — из модуля
Surveys в udevs_hrms_admin, недостающее дописано. Вкладки: Список ·
Шаблоны. В проде PR #15.

**Данные.** Опрос — `hr_surveys`: вопросы JSON SurveyJS строкой
в `definition`, тип (PICK_LIST), статус (STATUS: черновик · активный ·
завершён · архив, цвета в схеме), даты, анонимность, автор
`core_users_id`. Назначения — `hr_survey_participants` (ожидает ·
пройден · пропущен, `completed_at`), ответы — `hr_survey_responses`
(`answers` JSON, сотрудник, отдел).

**«Список»** — TABLE, за колонками схемы вычисляемые
(`useSurveyColumns`): число вопросов и замок анонимности, назначенные
аватарами, заполняемость полосой, меню строки (открыть, править,
дублировать черновиком, в архив, удалить).

**«Шаблоны»** — свой тип view `SURVEY_TEMPLATES`: восемь шаблонов
прототипа (eNPS, пульс, тренинг, адаптация, exit…), «Использовать»
открывает форму нового опроса с вопросами шаблона.

**Форма** — `/surveys/new` (`?tpl=`) и `?edit=true` (`SurveyForm`):
«Основное», «Сотрудники», «Вопросы» в SurveyJS Creator. Creator —
отдельный чанк (~450 КБ gzip), без ace-builds и вкладок темы и перевода,
цвета — наши токены (`survey-theme.css`, тёмная тема тоже). Импорт
SurveyJS JSON — в секции «Вопросы».

**Страница** `/surveys/$itemId` (`SurveyPage`): шапка со статусом,
«Пройти тест», «Скачать JSON», дублировать, удалить; KPI — они же
отбор; сотрудники с ответами (у анонимного — замок); статистика
по вопросам без survey-core (`model/survey`, тест рядом): eNPS для
шкалы 0–10, средняя для рейтинга, полосы для вариантов, тексты; CSV.

**Вкладка «Опросы» у сотрудника** (`EmployeeSurveys`): участие,
ожидающие, список назначений. «Пройти» — только на своей карточке
(привязанный пользователь — вошедший): ответ в `hr_survey_responses`,
назначение «Пройден». Роли «Сотрудник» нужны права — ERP-TEMPLATE, §4.

Проверено в браузере: список, шаблоны, форма, страница опроса,
прохождение сотрудником из своей карточки.

Ещё нет / заглушки:
- облачных функций назначения и прохождения (как
  `survey_assign_employees`, `survey_submit` в udevs-hrms-reports) —
  пишем через items API, без транзакции (`ponytail:` в `api/survey.ts`);
- «Напомнить» — уведомление-заглушка до Telegram-бота;
- лицензии SurveyJS нет — в конструкторе плашка;
- права роли «Сотрудник» на `hr_survey_*` заводятся руками.

«Дать вход» со страницы сотрудника — ERP-TEMPLATE, «Сотрудник,

## Дашборды (2026-10-12)

Решения — [ADR-0013](adr/0013-dashboard-menu-item.md), переписан
2026-10-12. Образцы: `DashNav` прототипа (`index.html`) и «Моя
аналитика» professio_app (`CustomAnalyticsView.tsx`).

**Хранение.** Все дашборды проекта — одно дерево «папка → дашборд →
виджеты» в `attributes.dashboards` пункта-хранилища: `LINK`
с `screen: "dashboards"` в корне меню, в дереве сайдбара не виден
(`useScreenMenu`). Заводится первой записью; перед каждой записью
перечитывается (`useSetMenuAttribute`). Тип `DASHBOARD` бэкенд
не принимает — `MENU_TYPES` закрытый (backend-notes). Править может
`update` на хранилище, суперадмин — всегда.

**Входы.** В CRM и HRMS первой стоит папка «Основное» с пунктом
«Дашборды» (`LINK`, `screen: "dashboards-entry"`, тип в узле —
`DASHBOARDS`); заведены через API 2026-10-12. Ведут на `/dashboards`
с текущим модулем.

**Экран `/dashboards`** (`features/dashboard`):

- сайдбар дашбордов: «Избранное», дерево «модуль → папка → дашборд»
  (модули — папки с `is_tab`, чужие папки — «Без модуля»), поиск,
  «+» (пустой дашборд, папка), «+» и удаление пустой папки,
  переименование двойным щелчком, скрыть/показать. Избранное
  и свёрнутые узлы — `localStorage` по проекту и пользователю;
- шапка как `.page-head`: путь, значок, название и описание правятся
  на месте; вкладки — дашборды той же папки и «+»;
- «Настроить»: черновик раскладки, «Сохранить» одной записью,
  «Отмена»; карточка — перетащить, размер, дублировать, настроить,
  убрать;
- редактор виджета — диалог с предпросмотром, как в professio:
  таблица → поле → расчёт → вид плитками → второе поле → название
  (собирается «Поле · Расчёт», пока не правили руками).

Виджет — карточка CHART со своей таблицей, строки — `get-list`
до 1000, «по N из M». Общее с CHART: `ChartSetup` (строкой и формой),
`ChartCard`, `chartTitle`. Виды переименованы по professio
(«Горизонтальные столбцы», «Кольцевая диаграмма», «Показатель»…);
«Ленточная диаграмма» перерисована по «Моей аналитике»: точка стадии
на левой границе колонки, S-переходы, градиент.

**Общие фильтры** (2026-10-12, `model/filters.ts`, `ui/DashFilters.tsx`):
объявляются в «Настроить» над виджетами — «Период» и «Запись таблицы»
(через поле-ссылку на неё: чип тот же `FilterChip`, с «Я» у сотрудников).
Значения — в адресе `f` по ключу («period», слаг таблицы). Виджет
в редакторе выбирает поле ответа (дата / ссылка, или ссылка → поле
справочника — `useViaGuids`) и свой отбор `FilterBar`; всё через «И»,
два фильтра на одно поле пересекаются. Не ответивший виджет пишет
«Не отвечает на фильтр». Сравнение с прошлым периодом посчитано
(`periodRange().previous`), но ждёт KPI. Не сделано: пояс проекта
(сейчас браузера), «за месяц целиком» у помесячных таблиц, «Я» через
`user_id_auth`, если вход не через таблицу фильтра. В браузере
не проверено.

**Не сделано** (шаги 4–5 ADR-0013):

- виды: KPI со сравнением, список записей, KPI-доля, разрез
  с формулами, прогресс к цели, заголовок блока, воронка
  по переходам; деньги по валютам;
- права на поля по раскладке роли (сейчас в списке полей видно,
  например, `password`), скрытие виджета без права на таблицу;
- `with_relations: false` и догрузка подписей связей;
  «Обновлено в»;
- перенос дашборда между папками и порядок вкладок; модуль
  и дашборд в крошках.

Открыто: процент в ленте — доля от всех строк (в образце — от первой
стадии). Не проверены в браузере переименование и удаление папки.

## Схема v2 (2026-10-15)

Схема данных пересобрана по модулям (`~/Downloads/FRONTEND_RU.md`
от 2026-10-14, источник — `omni4-v2/erp.dbml`). Ветка
`feat/schema-v2`. **В main не вливать, пока omni4 не переведут на v2**:

(`project-id f6e98ad0-…`, вход `Omni5test1@`).

Сделано в коде:

- Таблицы и колонки связей — новые имена (`hr_*`, `crm_*`, `core_*`;
  `departments_id` → `hr_departments_id` и т. д.).
- «Кто» и «о ком» разведены: `PEOPLE` = `core_users` (поля «кто»,
  фильтр «Я», «Все | Мои»), `EMPLOYEES` = `hr_employees`. Своя строка
  `core_users` — `user_id` токена; `session.getObjectIds()` кладёт её

- Страница сотрудника: бот и последний вход — из строки `core_users`
  с `hr_employees_id` = сотрудник; работодателя, роли и пункта
  «Пароль» больше нет (вход — у пользователя). Вкладки связей, которых

  `core_settings`, `core_currency_rates`, `crm_legal_entities`,

Не сделано:

- **В браузере на omni5 не проверено.** Только lint, typecheck, тесты.
- Что omni5 не хватает до omni4 (меню, view, подписи связей) —

- `core_users.timezone_id` в списке полей v2 нет — личный пояс

- Модуль может стоять без соседа (§5.5): экраны HRMS и справочники
  чужого модуля не прячутся, если его таблиц нет.
- `crm_tasks`, `crm_timeline` — своих экранов нет, трогать нечего.

## Типы view: что добавить

Бэкенд тип view не проверяет ([ADR-0006](adr/0006-chart-view-without-backend.md)),
так что каждый — фронтовая работа.

| В прототипе | У нас | Где в прототипе |
|---|---|---|
| table | TABLE | везде |
| board | BOARD | сделки, счета, задачи, контакты, компании, товары, план продаж |
| calendar | CALENDAR | сделки, счета, задачи, контакты |
| timeline | TIMELINE | сделки, счета, задачи |
| **list** | нет | сделки, счета, задачи, контакты, компании, товары, план продаж |
| **gallery** («Сетка») | GALLERY с `attributes.card: "person"` (ADR-0016), view заведён через API; карточка `PeopleGallery` годится любой таблице людей | сотрудники |
| **org** («Оргструктура») | ORG — только у сотрудников (`FIXED_VIEW_TYPES`), view заведён через API. Два дерева: сотрудники по руководителю, отделы (`features/hrms`); холст `OrgChart` общий. Третье — юрлицо → бизнес-юнит → локация — снято со схемой v2 | сотрудники |

Неделя/месяц в `schedule`, `employee`, `attendance` — отдельные экраны
графика, а не типы view; сделаны в HRMS (Посещаемость, График работы).
