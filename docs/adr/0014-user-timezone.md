# 14. Часовой пояс — личный, и только личный

Дата: 2026-10-08
Статус: принято

## Контекст

Пояс лежал в двух местах, и оба — не у человека: `org_settings.timezone`
(компания, раздел «Локализация») и `locations.timezone` (филиал). Фронт
не читал ни один: `DATE_TIME` показывался в поясе браузера
(`shared/lib/date-value.ts`). Функций, читающих их, в проекте нет —
серверная логика живёт в n8n, и n8n их тоже не читает.

Нужно: у каждого, кто входит в omni4, свой пояс, и по нему работает
и экран, и серверная логика.

Своего поля у пользователя ucode нет. В auth-сервисе `user.timezone_id`
был и удалён (`ucode_go_auth_service/migrations/postgres/000028`);
`GetByPK` отдаёт пустой `Timezone`.

## Решение

**Хранение.** `users.timezone_id` — имя IANA («Asia/Tashkent»).
`users` («Пользователи», папка «Ядро») — таблица входа типа клиента
«Сотрудник»: учётная запись, по `employees_id` один к одному со своим
сотрудником. `employees` — карточка человека, без входа. Пользователи
CRM и HR — одинаковые строки `users`. Это отход от D3 в PRD
(«`employees` — таблица входа»): `users` уже была настроена как таблица
входа, а карточка HR без полей входа не упирается в `items.go:708`
(backend-notes, «Строка таблицы входа без роли»).

Слаг `timezone_id`, а не `timezone`, потому что запись идёт через
`PUT /v2/user`: auth-сервис передаёт тело в таблицу входа
(`UpdateByUserIdAuth`, `ucode_go_object_builder_service/storage/postgres/
items.go:1590`), а та пишет каждое поле тела, у которого в таблице есть
колонка с тем же слагом. `timezone_id` — поле тела (`user_service.proto:243`).
Своей функции и права «изменять» на `users` не нужно.

Читается — из своей строки `users` (`user_id` токена): `GET /v2/user/{id}`
его не возвращает (`V2GetUserByID` берёт из строки только роль, тип
клиента, `active` и имя). Серверу, которому нужен пояс сотрудника, —
`users` по `employees_id`.

**Выбор пояса.**

| Где | Цепочка |
|---|---|
| Экран | профиль → браузер |
| Сервер | профиль → `Asia/Tashkent` |

Пустой профиль после входа один раз заполняется поясом браузера. Дальше
меняется только руками: командировка его молча не перепишет. Запасной
`Asia/Tashkent` на сервере нужен только тем, кто ещё не входил.

**Пояс профиля — везде**, включая посещаемость и табель: опоздание,
границы рабочего дня, переработки.

**Пояс компании и филиала удаляются** — из «Локализации», из `erp.dbml`
и из проекта.

**ADMIN** личного пояса не имеет: он входит через системную `user`,
поля там нет. Экран — по браузеру, сервер — `Asia/Tashkent`.

**Открыто — «мои записи».** Поля «кто» ссылаются на `employees`, а своя
строка в токене — из `users`. Автофильтр умеет брать сотрудника из claim
`tables` (`pkg/helper/automaticFilter.go:85`), но обычный `/v2/login`
кладёт туда то, что прислал клиент, без проверки
(`ucode_go_auth_service/grpc/service/session_service_v2.go:959`).
Решается до настройки ролей; к поясу не относится (STATUS.md).

## Последствия

- Табель зависит от личной настройки: сотрудник ташкентского офиса,
  выставив себе Москву, «приходит» на два часа раньше. Решено
  осознанно — альтернатива (учёт времени по поясу филиала) отклонена
  вместе с самим поясом филиала.
- Экран и сервер считают время одинаково: напоминание «на 9:00»
  и время в карточке — одни и те же 9:00.
- Значение уезжает через ручку с побочным поведением. Если ucode
  уберёт `timezone_id` из `UpdateUserRequest`, сохранение молча
  перестанет работать — тогда своя функция.
- `PUT /v2/user` не сверяет `id` тела с вызывающим
  (backend-notes, «Правка пользователя»). Пояс эту дыру не создаёт
  и не закрывает: профиль ходит тем же путём с самого начала.
