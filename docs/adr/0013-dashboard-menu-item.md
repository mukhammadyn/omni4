# 13. Дашборды — дерево в одном пункте меню, считаются на клиенте

Дата: 2026-10-02, пересмотрено 2026-10-05, переписано 2026-10-12
Статус: принято

## Контекст

В прототипе дашборды — отдельная страница `index.html` со своим
сайдбаром второго уровня (`DashNav`): «Избранное», дерево «модуль ERP →
папка → дашборд», поиск, «+ Новый дашборд» (пустой, папка, AI,
из шаблона). Над дашбордом — вкладки: дашборды той же папки и «+»
в папку. Общие фильтры сверху (Дата, Менеджер, Филиал — только
у CRM-дашбордов), KPI с изменением к прошлому периоду, воронка,
графики, таблицы-разрезы и списки. Один дашборд берёт данные
из нескольких таблиц: сделки, задачи, звонки, расходы на рекламу.

Образец «живого» дашборда — вкладка «Моя аналитика» в professio_app
(`new-crm/professio_app_69f844`, `CustomAnalyticsView.tsx`): виджет
собирается в диалоге (поле → расчёт → вид, с предпросмотром), пустой
экран зовёт «Добавить первый виджет», раскладка правится в режиме
«Настроить» с «Сохранить» / «Отмена». Там виджеты личные (в браузере),
только по сделкам, на `recharts` и `react-grid-layout`.

У нас есть view CHART (ADR-0006) — графики по строкам одной таблицы
в сетке на 12 колонок. Он даёт виджеты и раскладку, но не даёт главного:
смотреть на несколько таблиц сразу.

Отдельной сущности «дашборд» у бэкенда нет. Тип пункта меню —
не свободная строка: он сверяется с закрытым `MENU_TYPES`
(`object_builder config/constants.go:70`, проверка в `menu.go:36, 239,
919`), чужой отклоняется «unsupported menu type». А `attributes` —
JSONB, который сохраняется как есть (`storage/postgres/menu.go`).
`PUT /v3/menus` пишет строку целиком: поле, которого нет в теле,
обнуляется (backend-notes, «Меню»).

Точной агрегации с соблюдением прав у бэкенда тоже нет:
`POST /v2/items/:collection/aggregation` собирает SQL из тела запроса
и прав на записи не применяет (см. backend-notes, «Права и middleware»).

Что умеет `get-list` (`POST /v2/object/get-list/:slug`, `GetListV2`):

- **Права на записи применяет.** Автофильтр роли подмешивается в отбор
  (`object_builder.go:2441`), `count` считается по тому же отбору.
- **Права на поля — нет.** Отдаются все колонки; `field_permission`
  приходит только в раскладке и накладывается на фронте (backend-notes,
  «Права роли на поля отдаёт только раскладка»).
- **Фильтрует только по своим колонкам.** Список значений — `IN`
  (`build_query.go:332`), отбора через связь нет.
- **Выбрать колонки нельзя**, связи подтягиваются, пока не сказано
  `with_relations: false`. `limit` шлюз не ограничивает
  (`object_v2.go:45` только подставляет значение по умолчанию).

Модель данных ERP — `erp.dbml` (Ядро + CRM + HRMS + Проекты): таблицы
и слаги в ней фиксированные. Из неё для дашборда важно:

- Деньги всегда с валютой: `crm_deals.amount`, `crm_ad_spend.amount`,
  `crm_sales_plans.target_amount` — у каждой строки свой обязательный
  `currency`.
- `crm_ad_spend` и `crm_sales_plans` помесячные: `period` — первое
  число месяца.
- Филиала у сделок и звонков нет. `locations_id` есть у `tasks`
  и снимком у `employees`.
- Этапы принадлежат воронке (`crm_stages.crm_pipelines_id`), воронок
  несколько. Историю этапов пишет функция с момента запуска ERP —
  у перенесённых сделок её нет.

## Решение

### Хранение

**Все дашборды проекта — одно дерево в одном пункте меню.** Пункт-
хранилище — `LINK` с `attributes.screen: "dashboards"` в корне меню;
в дереве сайдбара его не видно (как пункт «Настройки»). Дерево лежит
в его `attributes.dashboards`:

```
dashboards: {
  folders: [{ id, module_id, title,
    dashboards: [{ id, title, emoji, description,
      filters: [...], widgets: [...] }] }]
}
```

Хранилище заводится при первом создании дашборда, если его нет.

**Модули дерева — из настоящего меню**: папки с `is_tab` (ADR-0010),
с их подписью и иконкой. Папка дашбордов ссылается на модуль по id;
модуля не стало — её дашборды уходят в группу «Без модуля», а не
пропадают.

**Вход из модуля.** В каждом модуле — пункт «Дашборды» (`LINK`
с `attributes.screen: "dashboards-entry"`). Он открывает общий экран
дашбордов (`/dashboards`, статичная страница) с развёрнутым своим
модулем. Тип `DASHBOARD` бэкенд бы отклонил, поэтому пункты различаются
`screen`, как «Настройки».

Сохранение собирается поверх свежего пункта: перед `PUT` хранилище
перечитывается, `attributes.dashboards` заменяется, остальные ключи
и поля строки едут как были. Ключ разбирается с недоверием, как
`charts` в ADR-0006: мусорный виджет, дашборд или папка пропадают,
а не роняют экран.

### Права

**Дашборды общие.** Видит экран тот, кто видит пункт-вход; читать
дерево — право `read` на хранилище. Создавать, переименовывать,
переносить, удалять дашборды и папки и править виджеты — тот, у кого
`menu_permission.update` на хранилище; суперадмину — всегда. Сервер
`PUT /v3/menus` по `menu_permission` не проверяет: запрет держит
интерфейс, как и у переименования.

Фильтры (в адресе страницы), избранное и свёрнутые папки — свои
у каждого и общих дашбордов не меняют.

### Экран

**Сайдбар дашбордов — как `DashNav` прототипа.** «Избранное», дерево
«модуль → папка → дашборд» со счётчиками, поиск по названию,
«+ Новый дашборд» в шапке и в подвале, «+» на папке. Избранное
и свёрнутые узлы — в `localStorage` с ключом по проекту и пользователю.
Сайдбар скрывается; на узком экране он выезжает поверх.

**Создать: «Пустой дашборд» и «Новая папка».** Новый дашборд —
«Без названия» в выбранной папке, сразу открывается; имя, эмодзи
и описание правятся в заголовке. «С помощью AI» и шаблоны — позже,
пунктов пока нет.

**Вкладки — дашборды той же папки**, как в прототипе, плюс «+» в эту
папку. Вкладок внутри дашборда нет.

**Пустой дашборд — как в professio:** «Соберите свою аналитику»
и «Добавить первый виджет».

**Виджет собирается в диалоге с предпросмотром**: таблица → поле →
расчёт → вид, плюс отбор и ответ на общие фильтры. Раскладка правится
в режиме «Настроить»: перетаскивание, размер, скрыть, дублировать,
удалить — и «Сохранить» / «Отмена». Запись — одна, по «Сохранить»:
«Отмена» возвращает снимок до правки.

**Рисует наш движок, не recharts.** Виджеты и сетка — от CHART
(`ChartCard`, `chartSeries`): 12 колонок, ширина 3–12, высота 1–3 ряда.

### Виджеты

Виды: всё, что умеет CHART, плюс KPI со сравнением с прошлым периодом,
список записей, KPI-доля, таблица-разрез, прогресс к цели, заголовок
блока, воронка по переходам. Все — в первой версии.

**Каждый виджет сам выбирает таблицу.**

**Числа считаются на клиенте по `get-list`.** Права на записи
соблюдаются, потому что ручка та же, что у таблиц. Количество
точное — его отдаёт `count`. Суммы, средние и разбивки — по выборке
до 1000 строк на таблицу; если строк больше, виджет пишет «по N из M».
Запрос идёт с `with_relations: false`: подписи связей виджету нужны
только для разбивки, и они догружаются по guid справочника. Виджеты
одной таблицы с одинаковым отбором делят один запрос.

**Права на поля дашборд накладывает сам.** Для каждой таблицы
загружается раскладка роли — `GET /v2/collections/{slug}/layout/{menu_id}`
с `menu_id` хранилища (чужую таблицу она отдаёт по любому пункту,
backend-notes). Виджет, который считает, группирует или фильтрует
по скрытому от роли полю, ведёт себя как виджет без права на таблицу.
Иначе сумма по `amount` или окладу из `hr_job_history` показала бы
роли то, что таблица ей не показывает.

**Виджет без права на чтение его таблицы** — по правам роли
(`useTablePermissions`), а не по ответу ручки — при просмотре скрыт,
сетка смыкается. В режиме правки он виден с пометкой, что у роли
без права его нет. Так же ведёт себя виджет по скрытому полю.

**Деньги разбиваются по валютам.** Суммы и средние по денежному полю
считаются отдельно по каждому значению поля валюты той же таблицы:
KPI показывает «12 400 USD · 85 млн UZS», график — серию на валюту,
разрез — столбец на валюту. Курсы (`currency_rates`) не применяются:
по какому дню пересчитывать, отчёт решить не может. Формула (CPL,
ROMI) считается только внутри одной валюты; где валюты разные, ячейка
пустая с пояснением. Прогресс к цели сравнивает план и факт
в валюте плана.

**Разрез и доля могут брать данные из разных таблиц, но только через
общий справочник.** Строки разреза — записи справочника (например,
`crm_sources`). Каждый столбец считается по своей таблице, сгруппированной
по полю, которое ссылается на этот справочник. Столбец-формула (CPL =
Расход / Лиды) считается из готовых столбцов. KPI-доля — два подсчёта,
каждый по своей таблице и со своим отбором. Произвольных соединений
таблиц нет.

**Воронка — два режима переключателем, одна воронка на виджет.**
Воронка (`crm_pipelines`) выбирается в отборе виджета: этапы разных
воронок в одну ленту не складываются.

- «По текущему этапу» — режим `funnel` из CHART.
- «По переходам» — когорта: сделки, созданные в периоде. Сделка дошла
  до этапа k, если её самый дальний этап — по `sort_order`, из истории
  `crm_deal_stage_history` и текущего — не раньше k. Поэтому лента
  не растёт слева направо, даже когда сделку перевели через этап,
  а сделка без истории (в том числе перенесённая) встаёт по текущему
  этапу. Отказ (`is_lost`) дошёл до того этапа, на котором отказали.
  История грузится для сделок когорты (`crm_deals_id` списком);
  больше 1000 сделок — «по N из M».

### Фильтры

**Общие фильтры объявляются на дашборде, а поле задаёт виджет.**
У CRM-дашборда — Дата, Менеджер, Филиал; у другого — свои. Значения
лежат в адресе страницы по ключу фильтра, поэтому одинаковый фильтр
не сбрасывается при переходе на соседнюю вкладку. Все виды —
в первой версии.

- «Период». Готовые значения хранятся словом («этот месяц», «квартал»)
  плюс свой диапазон. Готовый период — от начала единицы до сегодня;
  сравнение — с тем же числом дней от начала прошлой единицы
  (1–5 октября против 1–5 сентября). Свой диапазон сравнивается
  с отрезком той же длины прямо перед ним. Границы — в часовом поясе
  из настроек проекта, а если он не выбран — в поясе браузера.
  Помесячные таблицы (`crm_ad_spend`, `crm_sales_plans`) отвечают
  на период месяцами, которые он задевает, и виджет пишет «за месяц
  целиком», если период короче месяца.
- «Запись таблицы» (например, «Менеджер» по `employees`). Значение «Я» —
  `user_id` из токена, если вход идёт через таблицу этого фильтра
  (ту же строку берёт автофильтр бэкенда); иначе — запись, у которой
  `user_id_auth` совпадает с пользователем сессии. Записи нет —
  «Я» недоступно, а не «все».

Виджет говорит, каким своим полем отвечает на фильтр: прямой ссылкой
(`crm_deals.employees_id` на «Менеджер») или ссылкой через справочник
(«Филиал» для сделок — через `employees_id` → `employees.locations_id`).
Во втором случае сначала выбираются guid сотрудников филиала, потом
сделки отбираются по `employees_id` из этого списка — один запрос
сверху. Если подходящего поля нет, фильтр на виджет не действует,
и виджет это показывает. Свой отбор у виджета задаётся тем же
`FilterBar` и складывается с общими фильтрами через «И».

**«Обновить» и «Обновлено в»** — в первой версии, без автообновления.
**«AI-сводка»** — отдельной задачей, кнопки пока нет.

**Шаблоны дашбордов** опираются на фиксированные слаги `erp.dbml`
(`crm_deals`, `crm_stages`, `crm_deal_stage_history`, `crm_calls`,
`crm_ad_spend`, `crm_sales_plans`, `tasks`, `employees`). Они делаются
вместе с заведением схемы CRM в проекте. Экран дашбордов от схемы
не зависит и идёт первым.

## Что решено не делать

**Дашборд — отдельный пункт меню** (решение от 2026-10-02/05). Права
и запись по каждому дашборду, но дерево «модуль → папка → дашборд»
со своим сайдбаром пришлось бы собирать из пунктов, разбросанных
по меню, а вкладки внутри дашборда расходились с прототипом, где
вкладки — соседи по папке.

**Дашборды строками своей ucode-таблицы.** Это дало бы права на каждый
дашборд, правку одной записи вместо всего дерева и историю.
Цена — системная таблица в схеме каждого проекта и второй источник
правды рядом с меню. Вернёмся, если упрёмся в права по дашбордам
или в потерю правок.

**Личные дашборды, как «Моя аналитика».** Своего хранилища настроек
пользователя у бэкенда нет; в браузере дашборд не виден с другого
устройства и его не показать коллеге.

**recharts и react-grid-layout из professio.** Две зависимости и второй
движок графиков рядом с CHART: цвета вне наших токенов, а числа CHART
и дашборда разошлись бы. Свободное размещение по x/y не нужно сетке,
где порядок и ширина уже задают раскладку.

**Пересчёт валют по курсу.** См. выше: дата курса — решение бизнеса,
а не отчёта.

**Точные разбивки поштучными `count`.** Разбивку количества
по маленькому справочнику (этапы, источники) можно посчитать точно —
по запросу на значение. Пока не делаем: два пути счёта на один виджет
и десятки запросов на дашборд. Окупится, если «по N из M» станет
обычным видом.

## Цена

- **Права — на всё дерево.** Спрятать один дашборд или папку от роли
  нельзя; править может либо всё, либо ничего. Виджеты по недоступным
  таблицам и полям при этом скрываются сами.
- **Правки затирают друг друга.** `PUT /v3/menus` пишет пункт целиком:
  двое правят разные дашборды — сохранится последний. Перечитывание
  перед записью и одна запись на «Сохранить» сужают окно, но не
  закрывают его.
- **Дерево ездит одним куском.** Все дашборды проекта приходят одним
  пунктом меню и пишутся им же; с ростом их числа растёт и пункт.
- **Суммы неточны на больших таблицах.** Выше 1000 строк в отборе
  виджет считает по выборке и говорит об этом. Лечится только
  агрегирующей ручкой бэкенда с теми же правами, что у `get-list`.
- **Дашборд дорог по запросам:** по одному `get-list` на каждую пару
  «таблица + отбор», ещё по одному на сравнение с прошлым периодом,
  по раскладке на таблицу и по запросу на каждый фильтр через
  справочник. Грузится только открытый дашборд.
- **Права на поля — на совести клиента.** Скрытое поле приходит
  в ответе `get-list`, дашборд лишь не показывает его.
- **Суммы в разных валютах не сводятся.** Итога «всего в долларах» нет.
- **Избранное не переезжает между устройствами** — оно в браузере.
- **Старая админка ucode** увидит хранилище и входы обычными ссылками
  `LINK` без адреса и никуда не поведёт.
- **Шаблоны привязаны к `erp.dbml`.** Переименование таблицы или поля
  в схеме — правка шаблона.
- **Сведение таблиц — только через общий справочник.** Отчёт, которому
  нужно соединение по другому признаку, на дашборде не собрать.
